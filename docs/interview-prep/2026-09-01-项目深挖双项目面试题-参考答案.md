## 第一轮：项目介绍与技术选型

### Q1 请用 3 分钟介绍你的毕业设计「网上书店系统」

**参考话术（约 2 分 30 秒）**

> 我的毕业设计叫「云海书坊」，是一个前后端分离的网上书店前端应用。业务上我设计了四个核心模块：图书商城、阅读专栏、留言板、个人中心（含购物车、收藏、资料修改）。
>
> 技术上采用 **Vue 3 + TypeScript + Pinia + Vue Router 4 + Vite 5**。选 TS 是因为项目涉及 User、Book、Article、Message 四个主要数据模型，类型定义贯穿 store、api、视图三层，改字段时编译期就能发现引用错误，比纯 JS 开发踏实很多。
>
> 架构上我刻意做了**分层设计**：视图只调用 `api/` 层的异步函数，不直接碰数据。虽然当前是 mock 数据（用 `setTimeout` 模拟网络延迟），但后续接真实后端只需要重写 `api/index.ts`，视图零改动。
>
> 登录鉴权用 Vue Router 的全局守卫 `beforeEach` 检查 `localStorage` 中的用户对象，未登录访问受保护页面会被重定向到登录页，登录后通过 `query.redirect` 跳回原页面。
>
> 购物车和收藏都通过 Pinia 管理，并且把状态持久化到 `localStorage`，刷新不丢数据。
>
> 这个项目让我第一次完整实践了「分层架构 + 状态管理 + 路由守卫」的前端工程化套路，也让我意识到很多边界问题——比如 localStorage 存登录态只能作为演示方案，真实项目必须后端下发 Token。

**应对追问**

1. **为什么不用 Element Plus？** —— 毕设目的是展示前端基础能力，手写 CSS 更能锻炼布局和组件抽象能力；UI 库只是套样式，核心逻辑还是得自己写。
2. **和博客项目差在哪？** —— 博客是静态展示型，书店是有登录、状态、表单的交互式应用；书店因此引入了 TypeScript 做类型约束，复杂度更高。
3. **难点是什么？** —— 登录态的多处同步（用户信息 + 用户列表 + localStorage）容易改一处忘另一处，我通过让 `updateProfile` 统一收口来避免。

### Q2 两个项目都用了 Vue3 + Vite，说说"组件化开发"怎么理解？书店项目怎么划分组件？

**参考话术**

> 组件化就是把 UI 拆成可复用、可独立开发的单元。在 Vue 里每个 `.vue` 文件就是一个组件，封装了自己的模板、逻辑和样式（`<script setup>` + `<template>` + `<style scoped>`），对外通过 props 接收数据，通过 emit 抛出事件。
>
> 我的书店项目按"**通用 vs 页面**"划分：
> - `components/` 放通用组件，比如 `BookCard`（图书卡片）、`TheHeader`、`TheFooter`，这些不依赖具体业务场景，任何页面都能用。
> - `views/` 放页面级组件，比如 `BookListView`、`LoginView`，对应一个路由。
> - `views/profile/` 下还有嵌套的子页面组件（`CartPanel`、`FavoritesPanel` 等），配合 `<router-view>` 做二级路由嵌套。
>
> 组件之间通信：父子用 props/emit（如 `BookCard` 通过 emit 把"加入购物车"事件抛给父组件）；跨页面共享状态通过 Pinia（如购物车状态在 `BookDetail` 页面改，在 `ProfileView` 里的 `CartPanel` 读）。

**应对追问**

- **为什么 CartPanel 不放在 components/ 里？** —— 它只在个人中心二级路由里用，是"页面片段"，和父组件 `ProfileView` 耦合更紧，放在 views 下更符合职责。

## 第二轮：书店项目核心机制

### Q3 登录是怎么实现的？路由守卫怎么做鉴权？

**参考话术**

> 登录流程分三块：
> 1. **LoginView**：表单校验后调用 `userStore.login(username, password)`，它去 `localStorage` 里的 `bookstore_users` 表查找匹配的用户，匹配上就把**不带密码**的用户信息存入 `bookstore_user`，并把 `current` 设为登录态。
> 2. **路由守卫**：在 `router/index.ts` 的 `beforeEach` 里检查目标路由的 `meta.requiresAuth`，未登录就 `next({ name: 'login', query: { redirect: to.fullPath } })`。
> 3. **登录回跳**：`LoginView` 里 `route.query.redirect` 读到原始地址，登录成功用 `router.push` 跳回去。
>
> 我也明确它的**边界**：这是纯前端的演示方案。`bookstore_users` 里密码是明文存，`localStorage` 可以被浏览器开发者工具看到，前端校验也可以被绕过。真实项目里：
> - 密码必须后端**加盐哈希**存储（如 bcrypt），绝不明文
> - 登录态应该用后端下发的 **JWT Token**，前端存到 `sessionStorage` 或 `httpOnly cookie`
> - 通过 axios 拦截器统一携带 `Authorization: Bearer xxx`，遇到 401 统一跳登录
> - 路由守卫只作为 UX 优化，真正的权限校验必须在后端做

**代码锚点**
- `router/index.ts` L93-L105：`beforeEach` 守卫
- `stores/user.ts` L57-L67：`login` 函数
- `views/LoginView.vue` L33-L75：表单校验与回跳

### Q4 为什么用 Pinia？setup 语法和 options 语法怎么选？

**参考话术**

> Pinia 是 Vue 3 官方推荐的状态库，相比 Vuex：
> - **去掉了 mutations**（以前改状态必须通过 mutation 很繁琐，现在在 action 里直接改就行）
> - 支持 **setup 语法**：`defineStore('user', () => { ... })`，对 TypeScript 类型推导更友好，写起来更像普通 JS 函数
> - 没有 modules 嵌套地狱，每个 store 独立引入，按需使用
>
> 我在书店项目里用了两个 store：`user`（登录态、用户资料、收藏）和 `cart`（购物车）。之所以不放组件里：
> - 购物车状态要在 `BookDetail`、`ProfileView/CartPanel`、`TheHeader`（右上角购物车角标）三个地方读写，组件传值会层层透传
> - 登录态要在路由守卫里读，组件树拿不到
> - 这两个状态都要持久化到 `localStorage`，放在 store 里统一处理最干净
>
> `toggleFavorite` 同时改 `current` 和 `users` 表，是因为当前登录态是"缓存视图"，users 表才是"数据源"。如果只改一处，重新登录或者刷新后数据就会不一致。

### Q5 数据层是怎么设计的？为什么把数据写成 api 目录下的异步函数？

**参考话术**

> 我把数据访问封装在 `src/api/index.ts`，对外导出 `bookApi`、`articleApi`、`messageApi` 三个命名空间对象，每个方法都是 **async** 的，返回 Promise。
>
> 即使现在数据是本地数组（`data.ts`），我也用 `setTimeout` 模拟 100-200ms 的延迟，**刻意让调用方式与真实 HTTP 请求一致**。这样做的好处：
> - 视图层写的是 `const books = await bookApi.list()`，和将来调 axios 一模一样
> - 下周接入真实后端，我只需要重写 `api/index.ts`，把 `setTimeout` + 本地数组换成 axios 调用，**视图层零改动**
> - 项目结构清晰：视图层（views）→ 接口层（api）→ 数据层（data/后端），单一职责
>
> 至于 `package.json` 里装了 axios 和 json-server 但没用：是我预留的方案，计划后面用 json-server 起一个本地 REST 服务（mock/db.json），api 层改成 axios 调用，完成"前端 mock → 本地 mock 后端 → 真实后端"的三步演进。
>
> **真实接口的错误处理**：每个 api 方法应该包 try/catch，抛出业务友好的错误（如 `{ code, message }`），调用方用 `loading/error` ref 接收，UI 上做 loading 态和错误提示。我现在 mock 层是"不可能失败"的，但架构上已经把错误处理的坑位留好了。

**代码锚点**：`api/index.ts` L1-L37（`bookApi` 命名空间）

### Q6 购物车是怎么实现的？

**参考话术**

> 购物车放在 Pinia 的 `cart` store 里，数据结构是 `CartItem[]`，每项包含完整的 `Book` 对象和 `qty` 数量。
>
> 核心方法：
> - `addToCart(book, qty=1)`：先找有没有同款，有就累加数量，没有就新增
> - `updateQty(bookId, qty)`：用 `Math.max(1, qty)` 防止数量变成 0 或负数（0 应该走 `remove`，不应该走 `updateQty`）
> - `remove(bookId)` / `clear()`：删除单个 / 清空
> - `totalCount` / `totalPrice`：两个 `computed`，自动根据 items 重新计算
>
> 每次状态变更都调用 `persist()` 把 `items.value` 序列化进 `localStorage`，刷新不丢。
>
> **几个细节问题**：
> 1. `CartItem` 存整个 `book` 对象而不是只存 `bookId`：好处是渲染时不用再查一次图书表，缺点是如果图书信息被后台改了，购物车里还是旧数据。真实电商一般存 `bookId + qty`，详情实时拉。
> 2. **金额精度问题**：`qty * price` 是浮点累加，比如 `0.1 + 0.2` 在 JS 里不等于 0.3。真实电商应该把金额以"分"为单位存整数，展示时 `/100`，或者用 `decimal.js`。我项目里因为价格是固定的 .5/.0 结尾，累加不会出大问题，但这是隐患。
> 3. **换设备购物车就丢了**：localStorage 是本机绑定。真实项目里，登录态下购物车应该跟账号存后端，未登录时存本地、登录后合并。
> 4. **没有订单模块**：购物车结算的下一步应该有：确认页（合并地址+优惠券）→ 下单请求（防重复提交）→ 跳转订单详情。这是项目目前的缺口。

### Q7 搜索和筛选是怎么做的？

**参考话术**

> 搜索栏、分类按钮、排序下拉三个独立的状态：`keyword`、`activeCategory`、`sortBy`。
>
> - `watch(keyword)` 触发时做 **300ms 防抖**再请求，避免用户每敲一个字都发一次 API
> - `watch(activeCategory)` 直接触发（切换分类是离散事件，不需要防抖）
> - 排序放在前端 `computed` 里做（`displayBooks`），只对已经请求到的结果重排，不走 API
>
> **防抖 vs 节流**：
> - **防抖 debounce**：最后一次触发后等 N 毫秒才执行，期间再触发就重新计时。适合搜索、窗口 resize
> - **节流 throttle**：固定间隔执行一次。适合滚动事件、按钮防连点
>
> 我实现防抖的方式：在组件里维护一个 `searchTimer` 变量，watch 时先 `clearTimeout` 旧的，再 `setTimeout` 新的。
>
> **10 万本书的规模怎么办**：
> - 搜索必须交给后端（前端放不下全量数据）
> - 列表加分页（后端分页 or 虚拟列表 + 滚动加载）
> - 防抖要配合 `AbortController` 取消旧的未完成请求，避免乱序响应

### Q8 TypeScript 用在了哪些地方？

**参考话术**

> TS 在我项目里不是"装了但不用"，而是贯穿三层：
>
> 1. **数据模型**：`types/index.ts` 定义了 `Book`、`Article`、`Message`、`Reply`、`User` 五个 interface，11 个字段、6 个字段等都有明确类型
> 2. **API 层**：函数签名都带返回类型，比如 `list(params?: { keyword?: string; category?: string }): Promise<Book[]>`
> 3. **Store 层**：`ref<Book[]>([])`、`ref<User | null>(null)`，状态变化都有类型保护
>
> 几个用到的**高级类型**：
> - `Omit<Message, 'id'|'replies'|'date'|'likes'|'likedBy'>`：创建留言时不需要传 id 和时间（后端生成），用 Omit 把这些字段从 Message 类型里剔除，得到"入参类型"
> - `Partial<User>`：`updateProfile(patch)` 接收 User 的部分字段做更新，用 Partial 让所有字段变可选
> - `current.value!.id` 的感叹号是**非空断言**：告诉 TS "这里一定不是 null"，用于 `findIndex` 回调里。更安全的写法是用可选链 + 提前 return
> - `ref` vs `reactive`：我全部用 `ref`，因为 `ref` 在重新赋值时类型推导更稳定，`reactive` 解构会丢响应性
>
> **实际收益**：当我给 `User` 加了 `favoriteBookIds` 字段时，TS 立刻标红了 store 里初始化 user 的地方和 mock 数据里的 demo 账号，让我一次性修完，没有遗漏。

## 第三轮：博客项目 + 部署工程化

### Q9 博客是怎么上线的？讲讲 GitHub Actions 流水线

**参考话术**

> 我用 GitHub Actions 做 CI/CD，配置在 `.github/workflows/deploy.yml`。工作流逻辑：
>
> 1. **触发条件**：`push` 到 `main` 分支
> 2. **权限**：`contents: read`（读代码）、`pages: write`（发布 Pages）、`id-token: write`（Actions OIDC）
> 3. **并发控制**：`concurrency.group: pages, cancel-in-progress: true`，保证同一时间只有一个部署在跑，新的部署会取消旧的，节省时间也避免冲突
> 4. **build job**：
>    - `actions/checkout@v4` 拉代码
>    - `actions/setup-node@v4` 装 Node 20
>    - **`npm ci`**：按 `package-lock.json` 精确安装，和 `npm install` 的区别是 ci 严格按锁文件，会删除 node_modules 中不在锁文件里的包，速度更快、结果可复现，特别适合 CI
>    - `npm run build` 时注入环境变量 `BASE_PATH=/${{ github.event.repository.name }}/`，Vite 读到后会把所有静态资源路径加上这个前缀，让部署在 `/huangwenhong-blog/` 子路径下的资源能正确加载
>    - `upload-pages-artifact` + `deploy-pages` 把 dist 发到 Pages
> 5. **deploy job**：`needs: build`，部署完成后输出 URL
>
> 为什么部署两套（GitHub Pages + Vercel）？
> - **GitHub Pages**：国内可访问，作为主站给面试官看
> - **Vercel**：海外备用，国内被 DNS 屏蔽，但 Vercel 部署速度快、支持 history 模式 rewrites，方便我自己调试
> - 两边代码完全一样，只是部署目标和路由处理策略不同

**代码锚点**：`.github/workflows/deploy.yml`（整份配置）

### Q10 SPA 刷新 404，你两个项目分别怎么处理的？

**参考话术**

> **问题根源**：SPA 只有一个 `index.html`。history 路由模式下，访问 `/notes/1` 刷新，浏览器会向服务器请求 `/notes/1` 这个路径，静态托管上没有这个文件，就返回 404。
>
> **hash 路由天然避开这个问题**：URL 形如 `/#/notes/1`，# 后面的内容**不会**发给服务器，服务器永远只看到 `/index.html`。我的书店项目选了 hash 路由，就是因为它部署在纯静态环境（比如 U 盘演示、任意静态托管）时不需要服务器配置。
>
> **博客用 history 路由**：因为要 URL 干净（SEO 友好、分享链接好看），但要解决刷新 404：
> - **Vercel**：通过 `vercel.json` 配置 rewrites，把所有路径重写到 `/index.html`，交给前端路由接管
> - **GitHub Pages**：不支持 rewrites，我用了一个巧妙的兜底：把 404 页面（`public/404.html`）改成重定向页——先把用户想访问的完整 URL 存进 `sessionStorage.redirect`，再跳回首页（保留 `/<仓库名>/` 前缀不跳出本项目）；`index.html` 里有脚本从 sessionStorage 读回地址，用 `history.replaceState` 还原，前端路由接管渲染正确页面
>
> **`createWebHistory(import.meta.env.BASE_URL)`**：`BASE_URL` 就是 vite.config 里的 base。博客部署在子路径，不传 BASE_URL 的话，history 路由会基于根路径 `/`，而实际站点在 `/huangwenhong-blog/`，所有路由都会对不上。

**代码锚点**
- `huangwenhong-blog/vercel.json`：Vercel rewrites
- `huangwenhong-blog/public/404.html`：GitHub Pages 兜底
- `huangwenhong-blog/src/router/index.js` L62：`createWebHistory(import.meta.env.BASE_URL)`
- `222701002-黄雯宏-网上书店系统/bookstore-vue3/src/router/index.ts` L85：`createWebHashHistory()`

## 第四轮：安全、性能与开放设计题

### Q11 文章详情用了 v-html 渲染，有什么风险？

**参考话术**

> `v-html` 会把字符串当成 HTML 解析执行。如果字符串里含有 `<script>`、`<img onerror=...>`、`<a href="javascript:alert(1)">`，都会被浏览器执行，这就是 **XSS（跨站脚本攻击）**。
>
> 我的项目里 `article.content` 是我自己手写的静态内容，安全可控。但**留言板**如果也用 v-html 渲染用户输入，攻击者就能注入恶意脚本，窃取其他用户的 cookie/token，或者冒充管理员操作。
>
> **防御手段**：
> 1. **默认用 `{{ }}` 插值**：Vue 的 `{{ }}` 会自动把内容转义为纯文本，`<script>` 会变成字符串 `&lt;script&gt;`，不会执行
> 2. **需要渲染富文本时**：用 DOMPurify 等库做白名单过滤，只允许 `<p>`、`<h3>`、`<strong>` 等安全标签
> 3. **后端过滤**：提交时就把危险内容剥离
> 4. **Cookie 设 `HttpOnly`**：防止 JS 读到敏感 cookie
>
> 我的留言板目前是用 `{{ }}` 渲染用户输入（`MessageBoardView.vue`），所以是安全的；只有文章详情这种**受控的静态内容**才用 `v-html`。

### Q12 书店要做性能优化，从哪几方面入手？

**参考话术**

> 性能优化讲究**度量先行**，不是拍脑袋做。我按三层思路：
>
> **1. 网络层**（减少传输体积、请求次数）
> - **路由懒加载**（已做）：`component: () => import(...)`，每个页面独立 chunk，用户访问哪页才加载
> - **图片优化**（待做）：图书封面 12 张直接全加载，应该加 `loading="lazy"` 原生懒加载，并且用 WebP 格式（体积小 30%）、给不同屏幕做 srcset 响应式图
> - **代码分割细化**：`lodash` 这类库按需引入，不要整包
>
> **2. 渲染层**（减少首屏计算量）
> - **虚拟列表**：如果书目达到 1000+，列表只用 DOM 渲染可视区
> - **组件按需加载**：留言板的回复框做成异步组件，不编辑时不渲染
>
> **3. 缓存层**
> - **接口缓存**：同一分类短时间内多次切回不要重新请求
> - **资源缓存**：Vite 默认给资源文件名加 hash，配合服务器强缓存即可
>
> **怎么找瓶颈**：用 `rollup-plugin-visualizer` 看打包产物分布，Chrome DevTools 的 Lighthouse 看首屏评分和具体建议，Performance 面板看长任务。

### Q13 毕业设计做下来，最难的是什么？如果再做一遍会改什么？

**参考话术（开放题，结构最重要）**

> **难点**：最大难点是"数据一致性"问题——同一个状态要在多个地方保持同步。比如用户收藏一本书，既要更新 `current` 里的 `favoriteBookIds`，又要同步 `users` 表，还要持久化到 localStorage。刚开始我改一处忘另一处，经常出现"详情页显示已收藏，个人中心列表却没收藏"的 bug。后来我抽象出 `updateProfile` 统一收口，所有资料变更都走它，问题才消失。
>
> **如果再做一遍我会改**：
> 1. **一开始就接 json-server**：mock 数据层现在还是同步数组包异步壳，应该直接起一个本地 REST 服务，更贴近真实开发节奏
> 2. **补上订单模块**：购物车到下单是核心链路，缺了等于业务闭环没做完
> 3. **补单元测试**：store 的逻辑用 Vitest 测一遍，购物车加购、数量边界、登录失败这些用测试兜底，比人工回归靠谱
> 4. **金额用整数**：避免浮点累加隐患
>
> **收获**：完整走完了"需求→设计→开发→部署"的前端工程化流程，对 Vue 3 + TS + Pinia 的协作有了体感，对"演示项目 vs 生产项目"的边界（登录态、金额精度、安全）也有了清醒认识。

## 二轮迭代问题池答案要点

### 登录态：sessionStorage vs localStorage 怎么选？
- `localStorage` 持久化，关浏览器再开还在；`sessionStorage` 关标签页就清
- 登录场景：敏感场景用 `sessionStorage`（如银行），普通产品用 `localStorage` + 过期时间
- 最佳实践：token 存 `sessionStorage`，refresh token 存 `httpOnly cookie`

### Pinia：storeToRefs 是干嘛的？
- 解构 Pinia store 会丢响应性（因为 store 用的是 reactive 代理，解构变成普通值）
- `storeToRefs(store)` 把 store 的 state/getter 转成 ref，解构后仍保持响应性
- `storeToRefs` 只解构 state 和 getter；action 直接解构就行（是普通函数）

### 路由守卫：next() 传不同参数
- `next()` 放行
- `next(false)` 中断本次导航
- `next('/login')` 或 `next({ name: 'login' })` 重定向
- 异步守卫（如登录校验）：可以用 async 函数，但要保证每个分支都调了 next 或 return

### 防抖 + AbortController 取消旧请求
```ts
let controller: AbortController | null = null
watch(keyword, async () => {
  if (timer) clearTimeout(timer)
  controller?.abort()
  timer = setTimeout(async () => {
    controller = new AbortController()
    books.value = await api.search(keyword.value, { signal: controller.signal })
  }, 300)
})
```
解决：快速输入时前一次请求结果晚到覆盖后一次的问题。

### Vite 的 base 配置影响什么？
- 打包产物里所有静态资源路径（`<script src>`、`<link href>`、`<img src>`）
- 运行时 `import.meta.env.BASE_URL`
- 但不影响 `router` 的路径——所以路由要单独传 `createWebHistory(import.meta.env.BASE_URL)`

### 书店后端数据库建表
- `users`（id, username, email, password_hash, avatar, bio, created_at）
- `books`（id, title, author, cover, price, category, rating, stock, ...）

- `messages` + `replies`（含父表自引用）
- 关键索引：user_id, book_id, created_at

### 购物车下单防重复提交
- 前端：下单按钮点击后 `disabled` + loading 态；请求去重（Promise 复用或请求 ID）
- 后端：幂等键（客户端生成唯一 `requestId`，后端用 Redis 记录已处理）
- 扣库存用乐观锁或数据库行锁，避免超卖

### 加后台管理端
- 独立子项目或同项目多入口（Vite 多 entry）
- 抽 `@shared/types` 和 `@shared/api` 让前台和管理端共享
- 路由权限分级：普通用户 vs 管理员，通过 token 中的 role 判断

### 点赞接口幂等
- `POST /messages/:id/like`，服务端用 `(message_id, user_id)` 唯一索引
- 重复点赞返回当前 like 数，不累加
- 取消点赞用 `DELETE /messages/:id/like`

- `Vitest` 单测 store：登录流程、购物车加购去重、金额计算
- `@vue/test-utils` 组件测试：`BookCard` 的点击加入购物车事件
- `Playwright` / `Cypress` E2E：登录 → 浏览 → 加购 → 进入个人中心完整链路
